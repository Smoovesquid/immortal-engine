## The destination (one paragraph)

One continuous camera, **two representations**: a **2D zoomable strategic map** for planning travel, and a **tactical view where incidents happen**. Zoom all the way in and the 2D top-down **tilts and morphs into a 3D "D&D street view"** — terrain stands up into a battle map, characters/NPCs/monsters become **minis on pedestals**. Throughout, you play by *speaking* — "Take cover behind the barrel!" moves your token to the resolved spot, with tactical consequence (cover, line of sight, flanking). The 2D ink view and the 3D diorama are **two renderers over the same positional truth**, so 3D is a renderer swap, not a rewrite.

## Phase 1 — ONE_MAP: one coordinate space + one 2D continuous camera  ·  RENDERER LANE (parallel)

*Goal: replace the five-renderer patchwork with one world space and one Google-Maps-style 2D camera. This is the structural fix that kills the seam-bug genre.*

- **1.1 — World-space projection.** Implement `public/map/worldSpace.js` per ONE_MAP's coordinate model (nodes `node.x,y × NODE_WU=1000`; villages anchored at node centers, `PLACE_WU=4`; interiors fit to building footprint). **Pure + seeded; no engine writes.** Marker now reads engine room/interior → **subsumes VG-F3.**
  - *done-when:* every entity (node, village layout, interior, player, NPC, object) resolves to one `{wx,wy}` world-unit address; the player marker tracks the engine's current room and the inside↔outside transition; determinism green.
- **1.2 — One camera + LOD.** Unified camera `{cx, cy, z}` (center in wu, z = px/wu), wheel-zoom + drag-pan, with level-of-detail bands (county → settlement → building) so labels/detail fade in by zoom. Retire the scale tabs.
  - *done-when:* one continuous zoom from county to a single room, no tabs, no mode-switch; smooth pan/zoom.
- **1.3 — Route every surface through the one renderer.** The in-play compact map and the Map tab both render from `worldSpace` + the one camera (the old fixed-scale renderers stay on disk as fallback only).
  - *done-when:* the in-play map and the Map tab are the same renderer at different default zooms; the five-renderer seams are gone.
- **1.4 — Travel intent stays adjudicated.** Zooming out and clicking a far place is *travel intent the DM resolves* (time, roads, encounters, "you know of no such place") — the camera never teleports.
  - *done-when:* a far-click produces a DM travel adjudication, not a position write.

**Verify:** visual gate shows the marker tracking rooms + the inside↔outside flip (the VG-F3 acceptance test), at multiple zooms.

## Phase 2 — reactive tactical positioning, in 2D  ·  ENGINE + RENDERER (interleaves)

*Goal: prove the talk → commit → visible-token loop FLAT before any 3D. "Take cover behind the barrel" moves your dot, with crunch. This is the phase with real engine work.*

- **2.1 — Grounded positioned objects** *(ENGINE — schema; coordinate w/ engine lane).* Scenes carry real, *located* objects (the barrel is world state with a position + properties like cover-giving), not narrated flavor. Flip side of [[project_dm_invents_geography]] — you can't take cover behind a hallucinated barrel.
  - *done-when:* a furnished scene exposes positioned objects in world-space; WORLD_VERSION bumped per protocol; invariants + determinism green.
- **2.2 — Spatial-intent resolver ("spatial physics").** Propose/commit applied to space ([[IG-11]] sibling): the LLM *interprets* loose intent ("behind the barrel", "flank the wolf", "between me and him"); the **engine commits the exact deterministic cell** and adjudicates feasibility ("40 ft across open ground — you won't make it this turn"). LLM proposes, engine owns the geometry + the number.
  - *done-when:* a spoken spatial command resolves to a committed position deterministically; infeasible moves get an honest in-fiction adjudication (DM Test); never a teleport.
- **2.3 — Tactical crunch** *(escapeCombat — hot file, serial).* Position confers mechanics: cover bonus, line of sight blocks, flanking helps. The position means something.
  - *done-when:* cover/LOS/flank read from positions and affect rolls; consistent with the live combat engine.
- **2.4 — Render the moving token + relationships** *(RENDERER — parallel).* The marker animates to the committed spot; cover/LOS read on the 2D map.
  - *done-when:* the visual gate shows the dot move behind the barrel and the cover state legible on the map.

**Verify:** visual gate run where the Map Nit says "take cover behind the barrel" and the dot is seen moving there with cover applied.

## Phase 3 — the 3D tactical view  ·  RENDERER LANE (parallel, large)

*Goal: zoom all the way in → 2D tilts/morphs into a 3D battle diorama with minis. A renderer swap over the SAME world-space positions from Phase 1 — no new game logic.*

- **3.1 — WebGL scene over world-space.** A Three.js (or equiv) tactical renderer reading the identical `{wx,wy}` positions; camera pitches from top-down toward oblique as zoom crosses the tactical threshold.
  - *done-when:* the tactical scale renders in 3D from the same positions the 2D view uses; 2D remains the fallback.
- **3.2 — The tilt/morph transition** (the artful core — the "Google-Earth swoop"). Flat ink hands off to 3D meshes smoothly across the zoom; no jarring cut.
  - *done-when:* zooming through the threshold feels like one continuous move, not a scene change.
- **3.3 — Minis on pedestals.** Each character/NPC/monster renders as a stylized low-poly mini at its world-position. **Keyed to the bestiary** (creature type → mini), procedural / small library / AI-gen to keep the asset cost sane.
  - *done-when:* tokens become minis at the right positions; cover/movement read in 3D.
- **3.4 — Terrain meshes.** Biome data that paints 2D tiles extrudes to 3D (trees stand up, mountains rise), legible at a glance.
  - *done-when:* the tactical terrain matches the 2D biome truth in 3D.

**Guardrail (hold hard):** even in 3D street-view you **still play by talking** — never click-to-move. The 3D view is a window, same as the 2D ([[project_dm_only_verb]]).

## Sequencing & the parallel answer

```
Map-renderer lane (PARALLEL, own worktree, alongside engine lanes):
  Phase 1 (one space + 2D camera)  →  Phase 2.4 (render moving token)  →  Phase 3 (3D)

Engine coordination (INTERLEAVES — Homebase sequences vs engine lanes):
  Phase 2.1 positioned objects (schema bump)  →  2.2 spatial resolver  →  2.3 tactical crunch
```

- **Most of the map is genuinely parallel** (Phases 1 & 3 + render-halves) — start the renderer lane now.
- **Phase 2's engine pieces are the coordination point** — they touch schema/`playloop`/`escapeCombat` and go through the version-bump + serial-hot-file discipline. The renderer lane can build Phase 1 while Phase 2's engine work is scheduled.
- **3D (Phase 3) cannot start meaningfully until Phase 1's world-space exists** (it renders the same positions), but it does NOT need Phase 2 — a static 3D view of positions can land before reactive positioning.
